## 1. Problem Understanding - Describe the problem your system solves.
System purpose: The system manages event registrations for a single event with a waitlist. 
It allows users to register, cancel their registration, and check their status while automatically managing the waitlist.

Inputs to the system:

1. capacity
Description: The maximum number of users that can be registered for the event.
Type: Integer
Format: Numeric value
Valid Values: Non-negative integer.

2. user_id
Description: A unique identifier representing the user performing an action in the system.
Type: String
Format: Text
Valid Values: Non-empty unique string.

3. userAction
Description: The action requested by the user in the system.
Type: String
Format: Text command
Valid Values: "register", "cancel", or "status".


Outputs produced by the system:
systemResponse
Description:
1. The result returned by the system after processing a user request. The system returns users current registration status, or an error message if the action cannot be completed.
Type: UserStatus or error message
Format: Text message
Valid Values: Messages such as "registration successful" , "waitlisted", "registered", or an error explanation.


Primary goal of the system: The primary goal of the system is to provide a reliable and predictable registration process that automatically handles waitlist promotions and clearly reports system decisions to users.

## 2. Assumptions - List assumptions about the environment, users, or inputs.
A1: Event capacity is a non-negative integer.
A2: Each user is identified by a unique user ID.
A3: A user can only appear once in the system (either registered or waitlisted).
A4: The system processes user operations sequentially.
A5: The waitlist follows a FIFO (first-in-first-out) ordering.
A6: Users may query their registration status at any time.
---

## 6. Edge Cases - Describe unusual or boundary situations the system must handle.
EC1:
Event capacity is zero and a user attempts to register.
Expected system behavior:
The system should place the user directly into the waitlist because no registration slots are available.

EC2:
A user attempts to register again after already being registered or waitlisted.
Expected system behavior:
The system should reject the request and report a duplicate registration error.

EC3:
A user attempts to cancel a registration that does not exist in the system.
Expected system behavior:
The system should report an error indicating that the user is not found.

EC4:
A registered user cancels when there are users in the waitlist.
Expected system behavior:
The system should automatically promote the earliest user from the waitlist.

EC5:
A user on the waitlist cancels before being promoted.
Expected system behavior:
The system should remove the user from the waitlist and update the ordering correctly.

EC6:
Multiple registrations and cancellations occur rapidly in sequence.
Expected system behavior:
The system must maintain deterministic ordering and a consistent system state after each operation.

EC7:
A user queries their status immediately after successful registration.
Expected system behavior:
The system should return the updated status showing the user as registered.

EC8:
A user attempts to perform the same registration action multiple times.
Expected system behavior:
The system should reject duplicate registration attempts and report an error.
